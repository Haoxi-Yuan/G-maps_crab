# Abstract

When a cursor is dragged across Google Street View, the highlight overlay reorients itself: along the road on a road surface, parallel to the wall on a building facade. The visual effect implies a 3D geometric model behind the panorama, but where the geometry lives, what its structure is, and how it is registered to the panoramic image have not been documented in any public technical reference accessible to us. Through end-to-end browser instrumentation of an unmodified Street View session at the 20 Ghim Moh Road Market & Food Centre panorama (panoid `PeuYIfXn9uhqJykh9jTe1w`, Singapore), we recovered a plane-based geometric model embedded in the `/maps/photometa/v1` response. The decoded payload contains 140 plane equations and a 256 × 512 equirectangular index map assigning each panorama cell to one plane. The decomposition resolves into one sky proxy, 83 ground polygons (49.5% of pixels), 47 facades (10.9%), 8 roof segments and one oblique surface. The geometry occupies the same equirectangular coordinate system as the panoramic image, so registration is identity by construction rather than the result of a runtime alignment step. A direct ray–plane reconstruction yields a 77,949-vertex triangle mesh whose faces are the surfaces the browser uses for cursor hit testing. The cursor behaviour observed by users is fully explained as UV lookup followed by matrix-projected overlay rendering, with no real-time geometry inference required at the client. Extending the same pipeline to all 74 neighbour panoids exposed in the photometa response and pairing each panorama with its zoom-4 tile mosaic produces a 4 143 111-vertex colour-textured point cloud over the surrounding city block, exportable as a standard binary PLY for downstream semantic and ML processing.

# A cursor that knows about geometry

Google Street View is presented to the public as a panoramic image viewer. Moving the cursor onto the road overlays a directional arrow oriented along the road tangent; moving it onto a building wall replaces the arrow with a planar rectangle aligned to that wall's normal. The orientation tracks the surface continuously as the cursor moves, with apparent perspective foreshortening as the cursor approaches a vanishing point. The visual evidence rules out a pure 2D image viewer.

The visual evidence admits several architectural readings. The browser may be performing real-time geometric inference from the panoramic image, in the spirit of single-image depth estimation. The browser may be downloading geometric data alongside the image and using them to drive the cursor overlay. The browser may be making remote queries for each cursor event. Real-time client-side inference requires a model heavier than the latency budget of a smooth cursor would permit; per-event remote queries would generate one network round-trip per `mousemove` event and are ruled out by inspection of the network panel; the data-bundled-with-image reading remains the working hypothesis.

The aim is therefore to determine whether geometric data are transmitted to the browser, and if so to recover the carrying data structure, the alignment between the data and the panoramic image, and the minimal client-side computation that reproduces the observed cursor behaviour.

# A passive instrumentation pipeline

A clean reconstruction of the data flow requires observing the browser without altering its behaviour. We extended an existing Playwright-based scraping harness with three composable instruments, each one informing the next. A *route prober* loads a target URL inside a stealth-configured Chromium context and records the full request stream, console events, history transitions, DOM mutations and shadow `APP_INITIALIZATION_STATE` until the page becomes idle. An *interactive walker* enumerates every visible button on the loaded panel, clicks each one, and classifies the resulting behaviour into route change, in-page request burst or pure UI state shift, recovering between steps via `goBack()` or an `Escape` keystroke. A *Street View probe* augments the prober with hooks on `WebAssembly.{compile, instantiate}Streaming`, `HTMLCanvasElement.prototype.getContext`, and `XMLHttpRequest`/`fetch`, replays a deterministic mouse trajectory across the rendered viewport, and exposes a binding through which the page can ship captured WASM bytecode and full response bodies back to disk.

Stealth configuration was retained from the production scraper to avoid triggering the bot-detection paths that would otherwise change the data we observe. No interaction was scripted before the instrumentation was registered, and no requests were issued outside those that an unmodified browser session would generate.

# Reconnaissance: the POI page leaks the data layer

The first prober run targeted the parent place page (`/maps/place/...`). Beyond the obvious confirmation that Google Maps is a single-page application driven entirely by `pushState` and `replaceState`, with zero `<a href>` elements pointing to internal routes, the trace exposed three endpoints worth pursuing in isolation: `/maps/preview/place` for full POI metadata, `/maps/preview/passiveassist` for context-sensitive nearby suggestions, and `/maps/_/MapsWizUi/data/batchexecute` as the JSON-RPC channel through which UI actions are delegated. The same trace contained three street-view thumbnail requests to `streetviewpixels-pa.googleapis.com/v1/thumbnail`, with the panoid `PeuYIfXn9uhqJykh9jTe1w` already embedded in the URL.

The interactive walker then exercised 59 of the 65 visible buttons on the panel and classified their effects. Among the 14 buttons producing a `navigate-route-change`, the *Street View* thumbnail at viewport position (96, 928), 211 × 120 px, was the entry path of interest. Clicking it pushed a URL of the form `/maps/place/<name>/@<lat>,<lng>,3a,75y,<heading>h,90t/data=!3m8!1e1!3m5!1s<panoid>!2e0!...!7i13312!8i6656!...`, retaining the parent place identifier in the path and embedding the panoid in the data segment with the marker `!1e1` (panorama mode, distinct from `!1e2` for photo viewer). Only after this transition did the request stream load `loadSv.O.loader.js` and a paired `loadSv.O.wasm` module, confirming that the WebAssembly component is specific to the Street View renderer rather than a general Maps utility. The walker output also located the secondary entry — a 29 × 30 px Pegman icon at viewport position (1871, 1030), labelled *Browse Street View images* — which acts as a drag-target rather than an immediate navigation control.

# Six photometa responses for one panorama

The Street View probe was launched directly on the URL recovered by the walker. The mouse-trace phase moved the cursor across a 32-point grid spanning a ground sweep, a facade sweep and a vertical cross-section, dwelling 700 ms at each point. WebGL call counts ran at 500–660 calls per dwell across all phases, consistent with a continuously redrawing rasteriser, while WebAssembly hook counters returned zero — indicating that the WASM module instantiates inside a Web Worker rather than the main thread, and that worker-context hooks remain a future extension of the probe.

The body capture filter retained six responses to `/maps/photometa/v1?pb=...`, each 350–370 KB. Two responses described the focal panorama and its immediate neighbour at full geometric detail (140 and 195 planes respectively); the four others, served for further-out neighbours, contained only two-plane stubs (a sky proxy and a flat ground at 3.0 m depth). The pattern is consistent with a multi-resolution preloading strategy in which Google ships full geometry for the panoramas a user is most likely to walk into next, and bare placeholders for the ones a few hops away — explaining the perceived smoothness of street-view navigation without requiring on-demand fetches at hop time.

# Decoding the photometa payload

The geometric block lives at a fixed JSON path within the response: `$[1][0][5][0][5]`, a four-element array containing two binary blobs encoded in base64. The first blob (133 320 bytes after decoding for the focal panorama) carries the per-panorama plane equations and a per-pixel index map; the second blob (131 072 bytes), originally interpreted as a quantised depth map, is shown in the audit section below to be a categorical annotation-region map of unrelated semantic content.

The header of the first blob occupies eight bytes: a single-byte version identifier, a 16-bit little-endian plane count, two 16-bit little-endian dimensions giving the index map width and height, and one trailing offset byte. Reading the plane data at offset 8 — the layout suggested by the header — produced uniformly zero values for all 140 entries. Reading the trailing 16 bytes of the blob and reinterpreting them as four IEEE-754 32-bit floats gave the values $(0.0321, 0.1266, -0.9914, 0.2869)$, recognisable as a unit normal followed by a distance, with $n_z \approx -0.99$ identifying the surface as near-horizontal and oriented downward. The plane data are stored at the **end** of the blob, not at the beginning. The corrected layout consumes 8 bytes for the header, 131 072 bytes for the 256 × 512 index map (one byte per cell, identifying which plane each panorama pixel belongs to), and 2 240 bytes for 140 plane records of 16 bytes each. The total of 133 320 bytes accounts for the blob exactly.

Each plane record encodes the equation $\mathbf{n}\cdot\mathbf{p} = d$ where $\mathbf{n} = (n_x, n_y, n_z)$ is a unit normal and $d$ a positive distance from the panorama origin along that normal. The convention places $z$ along the local up-axis: the level ground appears as $\mathbf{n} = (0, 0, -1)$, $d = 2.5$ m, identifying the panorama camera as 2.5 m above the road surface — consistent with the height of a Street View capture vehicle. The second blob, addressed in the audit section, carries a categorical 256 × 512 grid of 73 region identifiers covering 14.7% of cells; despite our initial reading, it does not encode depth.

# A 140-piece geometric reconstruction of one street segment

Classifying each plane by the elevation component of its normal partitions the 140 entries into one sky proxy (zero-magnitude normal, 39.6% of panorama pixels), 83 ground planes (49.5%), 47 facades (10.9%), 8 roof segments and one oblique surface (Fig. 1). The decomposition is finer than typical schematic 3D city models. Rather than a single road plane, the surface in front of the camera is segmented into 83 polygons whose individual normals deviate from $(0,0,-1)$ by less than 5° and whose distances cluster in the 0.1–3.0 m range. The fragmentation tracks features that are visible in the source imagery: each crosswalk patch, kerb step, drainage gradient and pavement section receives its own plane. The same equirectangular grid is shared across the three encoding layers — sky band at the top, populated depth band along the horizon in the middle, and polygon mosaic at the bottom of Fig. 1.

# Alignment is identity, not registration

A common reading of the cursor behaviour is that geometry and image must be co-registered each frame. The decoded data contradict this reading. Three layers — the panorama image at 6 656 × 13 312, the index map at 256 × 512, and the annotation-region map at 256 × 512 — share the same equirectangular projection of a sphere centred at the camera. A pixel of the panorama at heading $\theta$ and pitch $\phi$ maps directly to the index-map cell at row $v = \lfloor (\pi/2 - \phi) H / \pi \rfloor$ and column $u = \lfloor (\theta + \pi) W / (2\pi) \rfloor$, with $W = 512$, $H = 256$. The same cell carries the plane index. There is nothing to register at runtime: the geometry was rasterised into the same coordinate system as the image at production time.

The corollary is that an arbitrary viewport pixel can be mapped to a plane through a chain of one matrix multiplication and one integer table lookup. Given the camera heading $h$, pitch $p$ and vertical field of view from the URL data segment, the camera-frame ray at viewport pixel $(x, y)$ is rotated into world frame, converted to $(\theta, \phi)$, mapped to integer $(u, v)$, and the index map returns the plane identifier. We implemented this projection over the 3 360 × 2 100 captured viewport using only NumPy (Fig. 4). The resulting category map aligns with the rendered street view to within one panorama cell — the road sits under the green polygons, the food centre's awning under the magenta–yellow facade band, and the opposite-side buildings under the cyan-green band — confirming that the equirectangular coordinate system and the URL-encoded camera parameters are the only ingredients the cursor logic needs.

# A 282 528-triangle mesh from one panoramic response

The geometric model can be promoted from a 2D index map back to an explicit 3D mesh through ray–plane intersection. For a panorama cell at $(u, v)$, the unit ray $\hat{\mathbf{r}}$ is computed from $\theta = (u + 0.5)/W \cdot 2\pi - \pi$ and $\phi = \pi/2 - (v + 0.5)/H \cdot \pi$, the assigned plane $i$ is read from the index map, and the ray–plane intersection $t = d_i / (\mathbf{n}_i \cdot \hat{\mathbf{r}})$ gives the 3D point $t \hat{\mathbf{r}}$ in panorama-local coordinates. Cells whose ray points away from their assigned plane ($t \le 0$) and cells classified as sky are dropped. For the focal panorama, 77 949 of the 131 072 cells produce valid 3D points; for the immediate neighbour, 74 099. The two panoramas can be composed in a shared world frame by translating each panorama's points by the local east–north offset derived from its lat–lng (recovered from the photometa node `[1][0][5][0][1][0]`).

Adjacent same-plane cells are connected into triangles. For each 2 × 2 cell quad in the index map, a pair of triangles is emitted only if all four vertices are valid and share the same plane index, with wrap-around at the longitudinal seam. The same-plane constraint preserves the discontinuities between adjacent surfaces and avoids elongated cross-plane triangles that would visually merge distinct walls. The combined mesh contains 152 048 vertices and 282 528 triangles, embedded as a single self-contained HTML file with a Three.js scene supporting orbit, mode toggling between mesh, wireframe and points, and per-vertex inspection of the source plane equation.

The same data also contain the road graph: the photometa response lists 74 neighbour panoid identifiers along with their lat–lng coordinates in `$[1][0][5][0][3][0]`, allowing us to overlay the drivable network on the geometric reconstruction.

# What the client actually computes

The cursor behaviour described at the start of the paper now resolves into a sequence with no remaining unknowns. A `mousemove` event on the canvas yields viewport coordinates $(x, y)$. The renderer's view matrix converts $(x, y)$ to a world-frame ray. The ray is converted to $(\theta, \phi)$ and indexed into the 256 × 512 plane map to obtain a plane identifier. The plane's 4-tuple $(\mathbf{n}, d)$ determines the orientation of the overlay: a near-horizontal $\mathbf{n}$ produces a road-tangent arrow; an $|n_z| < 0.2$ normal produces a facade-aligned rectangle; a zero normal (sky) suppresses the overlay. The overlay's perspective foreshortening is the inevitable consequence of rendering a 3D-positioned mesh through the same view matrix, not an additional computation. A WebAssembly module is loaded as part of the Street View renderer, and our hooks did not capture its bytecode because it instantiates inside a Web Worker; its likely role is frustum culling, accelerated UV-to-plane lookup at high cursor sample rates, and possibly resolution of the categorical annotation layer described in the audit, none of which are necessary to explain the cursor *behaviour* documented above.

The 15-minute mental model of "Google is doing real-time 3D reconstruction in your browser" should therefore be replaced. Google does the geometric reconstruction once, at the time the panorama is captured and processed; what the browser receives is a 256 × 512 byte map and 140 four-tuples, which together fit in 134 KB. The smoothness of the cursor experience is bought by the choice of representation, not by client-side compute.

The same instrumentation pipeline transfers to other Street View locations and to other Maps panels. Two extensions follow naturally from the present results. A Web Worker hook would capture the WASM bytecode and resolve its specific responsibility within the rendering pipeline. A multi-panorama prefetch crawl would invert the photometa neighbour graph into a city-wide drivable map carrying explicit geometry at every node — a 3D city model compiled directly from publicly accessible browser traffic.

# Interaction does not modify the geometric data

The cursor behaviour and the geometric encoding are linked through the index map; whether they are linked through the network is a separate question. We instrumented a second probe (`walk-streetview-interactions.js`) that scripts a deterministic sequence of mouse-wheel zooms, drag rotations and pitch adjustments after the panorama has settled, recording every request fired in each phase. Across 217 requests over seven phases (initial load, two zoom passes, two rotation drags, a full 360° spin, and a pitch up-and-down), the only photometa fetches occurred during the rotation and pitch phases, and they correspond to neighbour panoids being preloaded in anticipation of navigation, not to the geometric data of the focal panorama being reissued. Mouse-wheel zoom triggers the only zoom-5 tile fetches we observed (31 tiles in five wheel ticks), confirming that the highest-resolution tile pyramid level is fetched on demand rather than preloaded. Drag-rotate fetches additional zoom-4 tiles on the side that comes into view. None of these requests carry geometric payloads. The 256 × 512 index map and the 140 plane records described in the previous section are the same bytes whether the cursor is stationary, hovering, or executing a full 360° spin.

# From one panorama to a city-block colour-textured point cloud

Each photometa response carries a list of up to seventy-four neighbour panoids in `$[1][0][5][0][3][0]`, each tagged with its lat-lng coordinates and capture orientation. Building a city-block-scale model is therefore a matter of replaying the photometa request URL, substituting the focal panoid (in the `!2s<panoid>` segment of the `pb` parameter) for each neighbour. We confirmed that the request succeeds without authentication or session cookies (`fetch-neighbor-photometas.js`), with 74 of 74 listed neighbours returning ~350 KB payloads on first attempt. Of those, 52 carry full plane geometry (between 72 and 225 planes per response, median 158) and 22 are two-plane stubs identical in size to the four prefetched in the original probe. The bimodal pattern is consistent with the prefetch strategy described above: full geometry is shipped only for panoramas in a small radius around the focal capture; further-away neighbours act as navigation placeholders.

Each high-detail panorama is associated with up to 128 zoom-4 tiles at `streetviewpixels-pa.googleapis.com/v1/tile`, which `stitch_panoramas.py` reassembles into one 8 192 × 4 096 equirectangular JPEG per panoid (typically 4–6 MB). Because the geometric index map and the panoramic image share the same equirectangular coordinate system — the alignment-is-identity result established in Fig. 4 — each 3D point produced by ray–plane intersection inherits a unique source pixel in the associated panorama image. `build_rgb_pointcloud.py` performs this look-up and writes a single binary PLY plus an `.npz` archive with per-vertex `(x, y, z, r, g, b, plane_idx, pano_idx, class)`. For the Ghim Moh block the merged file contains 4 143 111 vertices spanning ±90 m around the focal panorama (78 MB binary PLY, 48 MB compressed `.npz`), readable directly by Open3D, CloudCompare, MeshLab and Blender.

A self-contained web viewer over the merged cloud poses a packaging problem: 4 M vertices times approximately 30 bytes of per-vertex data exceeds 100 MB, an HTML payload that browsers cannot embed inline without forced downsampling. The viewer (`build_megafused_viewer.py`) therefore writes the buffers as eight separate binary files (`positions.f32`, `rgb.u8`, `cls.u8`, `pano.u8`, `plane.u16` and two precomputed alternative colour buffers for plane class and plane-index hash), and a 12 KB HTML loads them through `fetch()` calls served by a 50-line Python `http.server` wrapper (`serve.py`). The full 4.14 M-point cloud renders interactively in Three.js with `PointsMaterial`, supporting a colour-mode toggle between true RGB, plane class and plane-index hash, plus per-class visibility filters and a per-point inspector that resolves plane equations on hover. No subsampling or level-of-detail is required at this scale; an octree-based streamer (Potree, Cesium 3D Tiles) becomes worthwhile when stitching multiple city blocks together, at which point the same `.ply` and `.npz` outputs feed directly into those toolchains.

The colour-textured point cloud is the natural input for downstream semantic enrichment. The plane equations recovered from photometa already separate sky, ground, facade, roof and oblique surfaces; semantic models trained on equirectangular imagery — or on perspective views derived from the panoramas — can populate a sixth field of class-label-per-point without re-running the geometry pipeline. The same scaffold supports object-detection bounding boxes mapped back through the equirectangular UV, large-language-model-mediated annotation of facade attributes (storefront type, façade material, signage), and direct urban-feature extraction once a city-block-scale corpus is accumulated. The probe pipeline produces a deterministic, reproducible bridge from the public Maps surface to a research-grade 3D dataset.

# Audit: what we got, what we missed, what we got wrong

The point cloud at any given panorama covers approximately 60% of the spherical image — every cell of the 256 × 512 plane index map is populated, but 39.6% of those cells are tagged with plane index 0, the sky proxy whose normal is the zero vector, and our pipeline correctly drops them as having no anchored geometry. The image at those cells is not only sky: it shows clouds, distant rooftops above the horizon line, *and* the cars, pedestrians, vegetation, and other smaller foreground objects that Google's own description of Street View's depth-map construction explicitly excludes from the encoded model. Google's published technical note on 3D navigation in Street View states that the depth map "encodes only the scene's dominant surfaces (e.g., building facades and roads), while ignoring smaller entities such as cars and people"; the 40% coverage gap therefore reflects a deliberate design choice, not a parsing failure. No other endpoint we observed across an active street-view session (`/v1/tile`, `/v1/thumbnail`, `/maps/preview/place`, `/maps/preview/passiveassist`, `/maps/preview/pegman`, the WASM loader, the JSON-RPC channel) contributes additional geometry, and an exhaustive scan of the photometa JSON for base64 strings longer than 1 000 characters returned only the two blobs already decoded.

An audit of every uncertain field in the photometa response, conducted across 30 of the 74 neighbour panoramas, resolves several initial readings. The 256 × 512 second blob, originally described as a quantised depth field, is not depth: blob2 values 1 and 2 correspond to mean ray-plane distances of 19.2 m and 13.3 m respectively, and value 3 jumps to 49.2 m, breaking any plausible quantisation curve. We then tested the alternative hypothesis suggested by Google's own description of Street View's "click-to-go" feature, in which a user clicks a screen point and is transported to the panorama nearest to that point's 3D location: implementing such a feature requires an image-space lookup table from pixel to destination panoid, exactly the shape blob2 has. For each non-zero blob2 ID, we computed the spatial centroid of its cells, converted that to a heading direction in the focal panorama's frame, and matched it against the headings to all 74 listed neighbour panoramas. The match is overwhelming: across 58 blob2 IDs (those with at least 8 cells), the median heading-alignment error is 2.94°, the mean is 5.76°, all 58 IDs match a neighbour within 30°, and 52 of 58 match within 15°. Several IDs match within 0.1° of a specific neighbour's bearing. Blob2 is the per-panorama click-to-go destination map: each cell tags which neighbour the cursor would teleport to if the user clicked there. The 28 distinct destinations across 58 IDs reflect the typical clicking pattern that several pixel regions converge on the same approach corridor, and the IDs missing from the destination set are those whose cells are too few or too scattered to form a single dominant heading.

The remaining unresolved fields fall into three groups. The pair-of-angles field at `[5][0][6]` carries two heading values per panorama: the median pairwise difference across 30 panoramas is 180.02° (consistent with front and back sub-camera headings on a typical dual-camera capture rig), but with a standard deviation of 37° driven by a long tail of non-180° pairs from rigs with different mounting geometry. The single-scalar field at `[5][0][13]` is present only on the focal panorama (74 of 74 neighbours fetched without a URL context have this field absent); its value 232.79° matches the URL-encoded heading 231.39° to within 1.4°, identifying it as the URL's heading parameter echoed back in the response. The `/maps/preview/pegman` endpoint returns a 2.5 KB JSON list of bounding boxes worldwide, the global street-view coverage atlas used to draw the blue overlay on the Maps overview, with no per-panorama data.

The audit also recovers a second carrier of semantic information that the original probe ignored. The field at `[5][0][9]` lists the panorama's POI bindings — explicit links from this capture position to one or more place identifiers, each carrying a name, a category and an icon URL. Across our 52 high-detail panoramas in the Ghim Moh block, 43 carry at least one POI binding, with 187 bindings in total spanning 128 distinct place names: hawker-centre stalls, retail businesses, post offices, kidney dialysis foundations, residential block addresses. Each panorama's POI list inherits to every 3D point produced from that panorama. The merged point cloud is therefore not only colour-textured but also POI-tagged: a query of the form *"what businesses are visible from this 3D location?"* returns a deterministic answer without any OCR or classification step.

The original 80 m hard cap on per-point distance is removed in the corrected pipeline. Empirically across 30 panoramas the 99.9th percentile of the plane-anchored distance distribution sits between 96 and 100 m, with an absolute maximum of 139 m — so the cap was forcing a 0.93% loss for no analytical benefit. The corrected pipeline uses a per-panorama 99.9th percentile as the adaptive cap, with a 200 m physical safety bound that never engages on real data. The total point count rises from 4 143 111 to 4 197 501, a 1.3% increase, distributed mostly into the 80–140 m band corresponding to taller buildings several blocks away.

# External corroboration

After the audit, we encountered a Google Research technical note on Street View's 3D navigation and modelling pipeline that independently describes the same data we recovered. The note frames the photometa geometry layer as a low-resolution panoramic *depth map* whose pixel values index a per-panorama table of 3D plane equations, exactly the layout we identified from byte-level analysis. It states that depth is computed via a *piecewise planar global model* fitted either to laser range scans (for newer capture vehicles) or to optical flow between successive images (for older platforms) — directly explaining the 83 ground polygons, 47 facades and 8 roof segments we observed, all of which have unit normals tightly clustered around either the local up-axis or a small set of horizontal directions. The note also states that the depth map "encodes only the scene's dominant surfaces ... while ignoring smaller entities such as cars and people," which is the missing context for the 40% coverage gap. Finally, the note explicitly describes the click-to-go feature whose data layer we identified empirically as the second photometa blob. The convergence between the byte-level audit and the published high-level description is end-to-end: every component of the photometa response that we successfully decoded — plane equations, plane index map, click-to-go destination map, neighbour graph, POI bindings, capture metadata — corresponds to a feature documented in Google's own writing, and every component the published note describes can be located in the bytes.

# Methods

**Browser harness.** All instrumented sessions ran inside a Playwright-driven Chromium 120 with a stealth configuration covering canvas-noise injection, WebRTC suppression, locale and time-zone normalisation, and tracking-resource passthrough. Resources that the production scraper blocks (heavy assets, tracking beacons) were unblocked for these experiments to ensure the network stream observed matches what an unmodified browser session would generate.

**Probe and walker.** The route prober (`probe-routes.js`) registers `add_init_script` hooks for `pushState`, `replaceState`, `popstate`, `hashchange`, and a `MutationObserver` reporter; it terminates after a configurable quiet window (15 s of no requests, no DOM mutations and no history events). The interactive walker (`walk-poi.js`) enumerates visible elements matching `[role="tab"]`, `[role="button"]`, `button` and `[jsaction]`, then clicks each in turn, recovers between steps via `goBack()` or `Escape`, and classifies the resulting URL transition or request burst into route change, path change, in-page load or pure UI state.

**Street View probe.** The probe (`walk-streetview-3d.js`) extends the route prober with hooks on `WebAssembly.compile`, `WebAssembly.compileStreaming`, `WebAssembly.instantiate`, `WebAssembly.instantiateStreaming` (capturing bytecode through `page.exposeBinding`), and on `HTMLCanvasElement.prototype.getContext` to wrap the returned WebGL context with call counters on `drawElements`, `drawArrays`, `bufferData`, `texImage2D`, `uniformMatrix4fv` and related methods. Response bodies for `/maps/photometa/v1` are saved verbatim. The mouse trajectory is a 32-point grid covering ground (10 points), facade (12 points) and a vertical cross-section (10 points), with `page.mouse.move(x, y, {steps: 20})` to ensure intermediate hover events fire.

**Geometry parsing and visualisation.** The 8-byte header of the first photometa blob is parsed as `uint8 version | uint16le plane_count | uint16le width | uint16le height | uint8 offset`. The index map of `width · height` bytes is read at offset 8; the plane table of `plane_count · 16` bytes is read at offset $8 + W H$. Each plane record decodes as four IEEE-754 little-endian floats giving $(n_x, n_y, n_z, d)$. Visualisations were produced with NumPy 2.4 and Matplotlib 3.10 inside the project's existing Python environment.

**3D reconstruction and viewer.** Per-cell ray–plane intersection was computed with NumPy. Inter-panorama placement uses the first-order equirectangular approximation $\Delta\text{east} = (\Delta\text{lng}) \cdot 111\,320 \cos(\phi_0)$ m, $\Delta\text{north} = (\Delta\text{lat}) \cdot 110\,540$ m. The two-panorama mesh viewer (`build_combined_viewer.py`) is a self-contained HTML document with embedded base64 buffers for vertex positions (`Float32Array`), vertex colours (`Uint8Array`), per-vertex plane indices (`Uint16Array`), per-vertex panorama tags (`Uint8Array`) and triangle indices (`Uint32Array`); rendering uses Three.js 0.160 with `MeshBasicMaterial` (vertex colours, double-sided) and `OrbitControls`, with a mode switch exposing the same buffers as a `Mesh`, a `Mesh` with wireframe overlay, or `Points`.

**Multi-panorama fusion.** Direct HTTP fetch of neighbour photometas (`fetch-neighbor-photometas.js`) replays the `pb` URL template captured from the focal probe with throttled concurrency. Tile stitching at zoom 4 (`stitch_panoramas.py`) downloads up to 128 tiles per panoid in parallel via `concurrent.futures.ThreadPoolExecutor`, pasting them into an 8 192 × 4 096 PIL canvas and saving as JPEG. RGB-coloured fusion (`build_rgb_pointcloud.py`) reads the parsed plane data, the index map, the second photometa blob and the POI binding at `[5][0][9]`, computes a 3D point per non-sky cell, samples its colour by integer-rounding the equirectangular UV into the panorama image, applies an adaptive distance cap (per-panorama 99.9th percentile, 200 m physical upper bound), and writes a single binary PLY and a compressed `.npz` archive carrying per-vertex `(x, y, z, r, g, b, plane_idx, pano_idx, class, b2_id)`. POI bindings are aggregated separately into `pointcloud_meta.json` so each panorama maps to a deterministic list of visible places. The full-fidelity Three.js viewer (`build_megafused_viewer.py`) writes a separate binary file per buffer; a small HTML (13 KB) loads them through `fetch()` requests, served by an `http.server`-based wrapper (`serve.py`) that adds CORS headers and an `application/octet-stream` MIME hint for the `.f32` / `.u8` / `.u16` extensions. The viewer exposes four colour modes — RGB, plane class, plane index hash, and `b2` annotation ID — and surfaces panorama-level POI tags in the per-point inspector.

**Field audit.** Every uncertain JSON field in the photometa response was tested empirically by `analyze_photometa_fields.py`. For the second photometa blob, blob2 values were cross-tabulated against ray-plane intersection distances (test of monotonicity, rejected) and against blob1 plane indices (concentration analysis); a per-cell overlay onto the original panorama image (`analysis_blob2_overlay.png`) was generated for visual inspection. The dual-angle field `[5][0][6]` was tested across 30 panoramas for ~180° pairwise difference. The scalar field `[5][0][13]` was tested for presence vs. URL context. The `/maps/preview/pegman` endpoint was fetched directly and its body inspected.

**Data availability.** The instrumentation scripts, the parsed photometa payloads, the index and depth binaries, the colour-textured PLY and `.npz` point clouds, the Three.js viewers and the local server helper are reproducible by running the pipeline against the URL in the abstract. All outputs were generated from publicly accessible Google Maps responses observed inside an unmodified browser session; no part of the harness modifies, replays or amplifies traffic to Google's servers.
